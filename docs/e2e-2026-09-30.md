## 它做什么

1. **启动所需状态**：在 `TemporaryDirectory` 里构造真实的
   `HistoryService(history_path=…)` / `DataStore(data_path=…)` / `OverlayService` /
   `SessionController` / `ActivityTracker`；前台事件与结算回调直接复用
   `MainWindow._on_foreground_change` / `MainWindow._on_session_record_saved`
   两个生产方法（以未绑定方式调用，`self` 换成只暴露这两个槽真正用到的协作者），
   因此改线会在这里暴露成失败，而不是被复制一份假接线悄悄绕过。
   全程不接触真实 AppData，也不写 QSettings（不调用 `save_app_config`）。
2. **走一遍核心流程**（三段）：
   - 会话 1：白名单应用前台 → 5s 专注；切到 `chrome.exe` → 1.2s 宽限期到期记 1 次
     分心并弹覆盖层 → 3s（覆盖层期间不计专注）；切回 `code.exe` → 覆盖层释放 →
     4s；按 Escape → 进入 60s 临时离开（走真实 `BreakWindow` 回调链，倒计时到 0
     自动回到 RUNNING）；再 48s → 第 60 tick 触发自然完成。
   - 会话 2：**不动**生产 `QTimer`（只把 interval 缩到 1ms），由事件循环自己跑到
     60s 边界完成。
   - 会话 3：15s 后用户手动 `terminate()`。
   - 计时只加速、不绕过；`ActivityTracker` 的取时改为注入的假单调钟（15s 定时器停掉），
     使每应用前台秒数完全确定。
3. **断言最终持久化结果**：直接从磁盘读 `history.json` / `daily_goals.json` /
   `daily_activity.json` 原始 JSON 逐字段严格相等；再新开一个 `HistoryService` 与
   `DataStore` 读同一批文件（等价进程重启后的反序列化）交叉核对；并检查原子写没在
   目录里留下 `.tmp`。

关键期望值不是抄运行结果，而是由脚本自己的事件编排推出来的：
`actual_focus_seconds == 60`、`app_focus_seconds == {"code.exe": 57}`（5+4+48，
覆盖层的 3 秒必须不记专注，另加一条 `60 - sum(...) == 3` 的守恒断言）、
`achieved_minutes == 2`（`60//60 + 60//60 + 15//60`）、`sessions_completed == 2`、
`sessions_terminated == 1`、前台使用 `{"code.exe": 110, "chrome.exe": 30}`。
